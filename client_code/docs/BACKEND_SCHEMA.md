# CCTV 백엔드 최소 스키마 및 구현 제약

- 정리일: 2026-10-05
- 상태: 사용자와 합의한 **구현 전 설계 기준**. 현재 코드에 구현되어 있다는 의미가 아니다.
- 범위: FastAPI + SQLite 기반 관리자 인증, 카메라 등록, 이벤트 저장 및 글로벌 인물 ID 연결.
- 원칙: 기본 테이블은 `server_runs`, `users`, `cameras`, `events` **네 개**로 유지한다. 별도 테이블·서비스·기능은 필요성을 설명하고 범위를 합의한 뒤 추가한다.
- 이 문서를 근거로 기존 코드를 자동으로 변경하지 않는다. 실제 구현은 사용자가 요청한 단계와 범위에서 진행한다.

## 1. 시스템 역할과 저장 경계

| 구성 | 역할 |
| --- | --- |
| PC 관제 프로그램 | 카메라별 영상 수신·추적, crop·궤적·클립 생성, OSNet 및 자체 CNN 작업 |
| PC FastAPI 백엔드 | 관리자 인증, 카메라·이벤트 API, SQLite 접근, 미디어 접근 제어 |
| Flutter 앱 | 로그인, 카메라별 실시간 영상 조회, 이벤트 히스토리·상세 조회 |
| 엣지노드 | 영상 송출, 장애 대비 녹화 및 복구 API 등 |

- SQLite 접근은 백엔드로 모은다. 추적·분석 결과는 API로 등록·부분 갱신한다.
- 프레임별 상태와 OSNet 비교 후보·특징값은 초기에는 추적 프로그램 메모리에서 관리한다.
- Refresh 토큰 상태는 **백엔드 단일 프로세스의 메모리**에서 관리한다.
- 이미지·영상은 파일 저장소에 저장하고, DB에는 저장소 기준 상대 경로만 기록한다.
- 글로벌 매칭용 OSNet과 이벤트 분석용 자체 CNN은 서로 다른 역할이다. CNN 출력 항목은 아직 미정이다.
- 기존 VLM은 자체 CNN으로 교체하고 Discord는 제거하는 방향이다. 이 문서는 그 변경을 구현하지 않는다.

## 2. 공통 자료형 및 DB 규칙

- PK는 `INTEGER PRIMARY KEY AUTOINCREMENT`를 기준으로 한다. 이벤트 ID와 서버 실행 ID의 재사용을 방지한다.
- 아래 `DATETIME`은 논리적 날짜·시간 타입이다. Python에서는 `datetime`으로 다루고 SQLite에는 UTC로 정규화한 일관된 형식의 문자열로 저장한다. 시간대·소수점 정밀도를 섞지 않는다.
- `TEXT(JSON)`은 유효한 JSON 문자열을 뜻한다. API에서 결과 구조를 검증하고 저장한다.
- 필수 값은 `NOT NULL`, 허용 상태·타입은 `CHECK` 또는 동등한 검증으로 제한한다.
- SQLite 연결마다 외래 키 검사를 활성화한다. 과거 이벤트를 보존하며 참조 대상을 무분별하게 연쇄 삭제하지 않는다.
- 모든 API는 인증·입력 검증을 수행한다. 정수 ID를 알고 있다는 사실은 접근 권한이 아니다.
- DB 초기화·과거 백업 복원 시에는 JWT 서명 키도 교체해, 되돌아간 실행 번호 때문에 과거 토큰이 다시 유효해지지 않게 한다.

## 3. 서버 실행 기록: `server_runs`

| 필드 | 타입 | NULL | 설명 |
| --- | --- | --- | --- |
| `server_run_id` | INTEGER | 불가 | PK, AUTOINCREMENT |
| `started_at` | DATETIME | 불가 | 실행 시작 시각 |
| `ended_at` | DATETIME | 허용 | 정상 종료 시각, 초기 NULL |
| `status` | TEXT | 불가 | `running`, `stopped`, `interrupted` |

### 정책

- 서버 시작마다 새 행을 생성한다. 현재 실행 ID는 실행 중 고정한다.
- 정상 종료 시 `stopped`와 종료 시각을 기록한다.
- 다음 실행에서 이전 행이 `running`이면 중복 실행이 아닌 것을 확인한 후 `interrupted`로 변경한다.
- 강제 종료 시각은 알 수 없으므로 복구 시각을 종료 시각인 것처럼 기록하지 않는다.
- Access JWT에 현재 실행 ID를 포함하고, 현재 값과 다르면 만료 전이라도 거부한다.
- Refresh 토큰의 메모리 기록도 현재 실행에 귀속시킨다.

## 4. 관리자 계정: `users`

| 필드 | 타입 | NULL | 설명 |
| --- | --- | --- | --- |
| `user_id` | INTEGER | 불가 | PK, AUTOINCREMENT |
| `username` | TEXT | 불가 | UNIQUE, 로그인 이름 |
| `password_hash` | TEXT | 불가 | 비밀번호 해시. 원문 저장 금지 |
| `created_at` | DATETIME | 불가 | 계정 생성 시각 |
| `updated_at` | DATETIME | 불가 | 계정 수정 시각 |

### 인증 정책과 제한

- 관리자 계정만 사용한다. `role`, `viewer`, `is_active`는 초기 범위에서 제외한다.
- 최초 관리자 생성은 PC 초기 설정에서 제공한다. 누구나 가입하는 관리자 회원가입 API를 공개하지 않는다.
- PC 관제 프로그램과 Flutter 앱은 같은 계정 체계를 사용하되 각각 로그인한다.
- Access JWT와 Refresh 토큰을 사용한다. Access 토큰 원문을 DB에 저장하지 않는다.
- `auth_sessions`, `refresh_tokens` 테이블은 만들지 않는다.
- 메모리에 로그인별 Refresh 토큰 해시, 사용자, 실행 ID, 만료 등 필요한 상태를 보관한다. PC와 앱의 토큰이 서로 덮어써지지 않게 한다.
- Refresh 갱신의 검증·기존 토큰 제거·새 토큰 등록은 원자적으로 처리한다. 단순 교체 방식은 과거 토큰의 상세 재사용 이력까지 제공하지 않는다.
- JWT 서명·허용 알고리즘·발급자·대상·만료·토큰 용도 및 현재 실행 ID를 검증한다. Refresh 토큰을 일반 조회용 Access 토큰으로 인정하지 않는다.
- 서버 종료·재시작 후 이전 Access·Refresh 토큰은 모두 거부한다.
- 단일 프로세스 메모리 정책이므로 여러 API worker 또는 여러 백엔드 인스턴스를 그대로 실행하면 안 된다. 필요해지면 공유 상태 설계를 다시 논의한다.
- 토큰 유효기간·갱신 시점·Refresh 형식은 구현 전 확정한다. 두 토큰을 사용한다는 이유만으로 무기한 로그인을 보장하지 않는다.
- 초기에는 개별 로그아웃 UI를 만들지 않고, 관제 프로그램 종료를 시스템 전체 종료로 처리한다.

## 5. 카메라 등록 정보: `cameras`

| 필드 | 타입 | NULL | 설명 |
| --- | --- | --- | --- |
| `camera_id` | INTEGER | 불가 | PK, AUTOINCREMENT |
| `name` | TEXT | 불가 | 관제 화면·앱 표시 이름 |
| `camera_type` | TEXT | 불가 | `webcam`, `edge_node` |
| `webcam_index` | INTEGER | 조건부 | 웹캠 장치 번호 |
| `rtsp_url` | TEXT | 조건부 | 엣지노드 영상 수신 주소 |
| `edge_api_base_url` | TEXT | 허용 | 엣지노드 복구·장치 API 기본 주소 |
| `is_enabled` | INTEGER | 불가 | 0 또는 1, 기본 1 |
| `created_at` | DATETIME | 불가 | 등록 시각 |
| `updated_at` | DATETIME | 불가 | 수정 시각 |

### 제약 및 동작

- `webcam`: `webcam_index` 필수, RTSP·엣지노드 API 주소는 NULL.
- `edge_node`: `rtsp_url` 필수, `webcam_index`는 NULL. 복구·장치 API 사용 시 `edge_api_base_url`도 필수.
- RTSP와 API 주소를 구분한다. 호스트·포트가 반드시 같다고 가정하지 않는다.
- 등록과 연결 성공을 구분한다. 연결 실패가 나도 등록 정보는 유지하고 재시도할 수 있다.
- `is_enabled`는 사용 설정이며 실제 연결 상태가 아니다. 연결 상태는 실행 중 별도로 관리한다.
- 웹캠 장치 번호는 USB 연결 상황에 따라 달라질 수 있으므로 재선택을 지원해야 한다.
- 각 카메라는 독립적인 수신·추적기·재연결·녹화 상태를 갖는다. 한 카메라 장애가 다른 카메라를 종료시키면 안 된다.
- 초기에는 카메라 삭제 대신 비활성화를 사용한다.
- 엣지노드 자격증명, 장치 등록 인증 및 앱용 실시간 스트리밍 방식은 아직 미정이다. 이 스키마만으로 장치 보안·실시간 송출 구현이 완성되는 것은 아니다.
- 앱에 원본 RTSP 주소나 자격증명을 무조건 반환하지 않는다. 앱의 시청 권한과 송출 방식에 맞춘 API 계약을 별도로 정한다.

## 6. 이벤트: `events`

| 필드 | 타입 | NULL | 설명 |
| --- | --- | --- | --- |
| `event_id` | INTEGER | 불가 | PK, AUTOINCREMENT |
| `event_type` | TEXT | 불가 | `person_detected`, `connection_error` 등 |
| `server_run_id` | INTEGER | 불가 | FK → `server_runs.server_run_id` |
| `camera_id` | INTEGER | 불가 | FK → `cameras.camera_id` |
| `tracking_run_id` | INTEGER | 조건부 | 서버 실행·카메라 안의 추적기 실행 번호 |
| `local_person_id` | INTEGER | 조건부 | 추적기가 반환하는 로컬 인물 ID |
| `global_person_id` | INTEGER | 허용 | 동일 인물 그룹 번호, 초기 NULL. FK 아님 |
| `global_match_status` | TEXT | 불가 | 글로벌 매칭 상태 |
| `crop_path` | TEXT | 조건부 | 저장된 crop 이미지 상대 경로 |
| `cnn_status` | TEXT | 불가 | CNN 처리 상태 |
| `cnn_result` | TEXT(JSON) | 허용 | 초기 NULL, 실제 출력 구조는 미정 |
| `trajectory_status` | TEXT | 불가 | 이동 궤적 처리 상태 |
| `trajectory_path` | TEXT | 허용 | 궤적 이미지 상대 경로, 초기 NULL |
| `clip_status` | TEXT | 불가 | 클립 처리 상태 |
| `clip_path` | TEXT | 허용 | 클립 영상 상대 경로, 초기 NULL |
| `message` | TEXT | 허용 | 연결 오류 등 카드 설명 |
| `occurred_at` | DATETIME | 불가 | 인물: crop 촬영 시각, 오류: 오류 감지 시각 |
| `created_at` | DATETIME | 불가 | DB 등록 시각 |
| `updated_at` | DATETIME | 불가 | 마지막 갱신 시각 |

### 생성 조건

| 항목 | 인물 탐지 이벤트 | 연결 오류 등 상태 이벤트 |
| --- | --- | --- |
| 추적 실행·로컬 ID | 필수 | NULL |
| crop 경로 | **저장 완료된 경로 필수** | NULL |
| 글로벌 ID | NULL | NULL |
| 글로벌 매칭 상태 | pending | not_applicable |
| CNN·궤적·클립 상태 | pending | not_applicable |
| CNN 결과·후속 자료 경로 | NULL | NULL |
| message | 선택 | 상황 설명 |

- crop 저장 성공 후 인물 이벤트를 생성한다. 새 로컬 ID가 나왔다는 이유만으로 crop 없는 인물 이벤트를 먼저 만들지 않는다.
- crop 저장 실패 시 이벤트를 등록하지 않고 재시도 정책에 따른다.
- 준비 전 결과를 정상 판정이나 점수 0으로 채우지 않는다. NULL과 실제 결과를 구분한다.
- 본 초안은 하나의 이벤트에 대표 crop·궤적 이미지·클립이 각각 하나인 구조다. 여러 클립이나 재분석 이력이 필요하면 별도 논의한다.

### 복합 식별 조건

한 로컬 추적당 인물 이벤트 하나를 생성한다. 다음 조합에 대해 **인물 이벤트에만 부분 UNIQUE 인덱스**를 적용한다.

```text
(server_run_id, camera_id, tracking_run_id, local_person_id)
WHERE event_type = 'person_detected'
```

- 이것은 덧셈이 아니다. 네 컬럼 값을 각각 비교하는 복합 식별 조건이다.
- `event_id`는 별도의 PK이며 모든 후속 결과 업데이트는 이 ID를 사용한다.
- `tracking_run_id`는 별도 테이블의 FK가 아니다. 해당 서버 실행·카메라 안에서 추적기 ID 체계를 초기화할 때 증가시키는 번호다.
- 일시적 네트워크 끊김만으로 반드시 번호를 바꾸지는 않는다. 추적기를 초기화하면 번호를 바꾼다.
- 서버 재시작 시 추적 실행 번호가 1부터 다시 시작해도 서버 실행 ID가 달라 구분된다.
- 같은 추적 실행 안에서 서로 다른 사람에게 로컬 ID를 재사용하지 않는 것이 전제다. 현재 ID 보정기가 이 전제를 지키는지 구현 시 확인한다. 이미 종료한 로컬 ID를 재사용하는 추적기라면 추적 생명주기를 추가 구분해야 한다.
- POST 응답 유실 후 재시도에는 동일 복합 식별값으로 기존 이벤트를 반환하거나 충돌을 명확히 처리한다. 중복 이벤트를 만들지 않는다.

| event_id | server_run_id | camera_id | tracking_run_id | local_person_id | global_person_id |
| --- | --- | --- | --- | --- | --- |
| 101 | 10 | 1 | 1 | 1 | 101 |
| 102 | 10 | 1 | 2 | 1 | 102 |
| 103 | 10 | 2 | 1 | 1 | 101 |

위 예시에서 101·102는 같은 카메라의 서로 다른 추적 실행이며, 101·103은 다른 카메라의 관측이지만 동일 인물로 연결된 기록이다.

### 상태 값

| 대상 | 허용 상태 |
| --- | --- |
| 글로벌 매칭 | pending, processing, deferred, assigned, failed, interrupted, not_applicable |
| CNN·궤적·클립 | pending, processing, ready, failed, interrupted, not_applicable |

- `pending`: 대기 / `processing`: 진행 / `deferred`: 매칭 판단 보류.
- `assigned`: 글로벌 ID 결정 / `ready`: 결과·파일 준비 완료.
- `failed`: 처리 오류 / `interrupted`: 종료·장애로 중단 / `not_applicable`: 해당 없음.
- `assigned`이면 글로벌 ID가 존재해야 하고, `ready`이면 해당 결과 또는 경로가 존재해야 한다.
- 작업별로 필요한 필드만 PATCH한다. CNN 업데이트가 이미 저장된 클립 경로 등을 NULL로 덮어쓰지 않게 한다.
- 비동기 작업에는 재사용될 수 있는 로컬 ID 대신 `event_id`를 전달한다. 작업 결과·상태 갱신은 해당 이벤트와 실행에 맞는지 확인한다.

## 7. 글로벌 ID 발급·동시 관측 정책

```text
crop 저장 → 이벤트 생성(global_person_id = NULL)
    ↓
OSNet 특징 추출 → 중앙 매칭 대기열
    ├─ 기존 인물과 매칭 → 기존 글로벌 ID 연결
    ├─ 신규 인물 판단 → 현재 event_id를 글로벌 ID로 사용
    └─ 판단 불확실 → NULL 유지, deferred, 추가 관측
```

- `global_persons` 테이블은 만들지 않는다.
- 글로벌 ID는 최초 신규 인물 이벤트의 번호에서 가져온 **그룹 식별값**이다. `events`를 참조하는 FK가 아니다.
- 최초 이벤트가 삭제되어도 다른 이벤트의 그룹 번호는 유지한다. 이벤트 ID를 재사용하지 않는다.
- 특징값과 글로벌 ID를 묶은 최근 비교 후보는 초기에는 메모리에 보관한다. DB의 crop 경로만으로 OSNet 유사도를 계산할 수 있는 것은 아니다.
- 재시작 후에도 기존 이벤트의 글로벌 ID는 보존되지만, 과거 인물의 재식별 후보 복원은 초기 범위에 포함하지 않는다.
- 로컬 추적 종료와 글로벌 후보 만료를 구분한다. 짧은 재등장을 연결할 수 있도록 최근 사라진 후보를 일정 시간 유지한다. 유지 시간·임계값은 검증 후 정한다.
- 후보 비교·연결/신규 결정·DB 반영·메모리 후보 반영은 중앙 담당 하나가 순차 처리한다. ID 발급 시점만 잠그는 것으로 끝내지 않는다.
- A의 결과를 후보 목록에 반영한 뒤 B의 판단을 시작한다. DB 반영 실패를 성공처럼 처리하거나 메모리와 DB를 불일치 상태로 진행하지 않는다.
- 영상 수신·특징 추출·CNN 전체를 직렬화하는 것은 아니다. 글로벌 연결 결정을 중앙에서 조정한다.
- 다른 카메라에서 동시에 관측되는 것은 동일 인물일 수 있다. 같은 카메라에서 동시에 관측된 서로 다른 두 사람은 같은 글로벌 ID로 묶지 않는다.
- 순차 처리는 동시성으로 인한 중복 발급을 줄이지만, OSNet 오인식을 해결하지는 못한다. 낮은 품질·모호한 후보는 추가 crop으로 재평가한다.
- 고정된 겹침 카메라에서 호모그래피는 추후 보완 수단이다. 초기 필수 구현으로 넣지 않는다.

## 8. 앱 표시와 API 경계

- 목록 카드: crop 또는 상태 아이콘, 이벤트 종류, 발생 카메라, 발생 시각.
- 인물 카드 선택: crop, CNN 결과, 궤적, 클립을 표시하는 상세 화면.
- 오류 등 상태 이벤트: 초기에는 상세 화면 없이 카드 설명으로 끝낸다.
- 미완료·실패·중단 자료는 상태에 맞는 기본 표시를 사용한다.
- 초기 상세 갱신은 주기 조회 방식으로 시작할 수 있다. DB 갱신 자체가 앱 화면 갱신을 보장하지는 않는다.
- 알림 조건은 글로벌 ID와 crop이 모두 준비된 시점이다. 후속 자료가 완성될 때마다 새 이벤트나 중복 알림을 만들지 않는다.
- 푸시/앱 실행 중 알림의 전달 방식과 중복 발송 방지·재시도는 아직 미정이다. 알림 테이블이나 서비스를 임의로 추가하지 않는다.
- 실시간 영상과 저장 미디어에도 접근 제어가 필요하다. 실제 경로·원본 접속 자격증명을 앱 응답에 노출하지 않는다.
- 히스토리는 `(occurred_at, event_id)`로 안정적으로 정렬·페이지 조회한다. 카메라별 조회 등 실제 쿼리에 맞춰 인덱스를 추가한다.

## 9. 시작·종료·복구

### 시작

```text
중복 실행 방지 → 로딩 화면 → 백엔드 시작 → DB 연결
→ 새 server_run_id 생성
→ 이전 실행의 미완료 작업·실행 상태 정리
→ DB 반영 완료 → 백엔드 준비 확인 → 관리자 로그인 → 관제 화면
```

- 복구 작업을 끝내기 전에 외부 요청을 정상 처리 가능한 상태로 열지 않는다.
- 이전 실행의 pending·processing 및 글로벌 매칭 deferred는 interrupted로 변경한다.
- 완료된 결과·경로·글로벌 연결은 보존한다. 초기에는 중단 작업을 자동 재실행하지 않는다.
- 백엔드 시작 실패 시 오류와 재시도 경로를 제공한다.
- 로그인 후 카메라 자동 시작 여부는 별도 정책으로 정한다.

### 정상 종료

```text
종료 중 전환 → 신규 외부 요청·작업 차단
→ 영상 수신 중단 및 녹화·클립·분석 정리
→ 가능한 결과 저장, 미완료 항목 interrupted
→ 인증 갱신 상태 폐기·DB 반영
→ AI 작업·자식 프로세스 정리 → 백엔드 종료 → 관제 프로그램 종료
```

- 결과 저장용 내부 통신은 마지막 DB 반영까지 유지한다.
- 종료 대기는 제한한다. 초과 시 이 프로그램이 실행한 자식 프로세스만 종료한다.
- 관제 프로그램이 종료되면 녹화·분석·앱 접속도 중단된다.

### 파일 처리

- 임시 파일 작성 → 파일 저장 마무리 → 최종 파일명으로 변경 → DB 경로·ready 반영 순서로 처리한다.
- ready 상태의 자료만 정상 미디어로 제공한다.
- 파일 저장과 DB 커밋은 하나의 원자적 작업이 아니다. 중간 종료로 남는 임시·미참조 파일을 정리하는 정책이 필요하다.
- 초기에는 미완성 영상을 자동 복구하지 않는다. 정리 시 완료 파일을 무조건 삭제하지 않는다.

## 10. 구현 전 남은 결정과 검증 범위

1. Access·Refresh 유효기간, 자동 갱신 시점, Refresh 형식과 안전한 클라이언트 보관 방식.
2. OSNet 비교 후보 유지 시간·품질 기준·유사도 임계값·모호한 판단 재시도 정책.
3. 자체 CNN 결과 JSON 구조 및 재분석 필요 여부.
4. 카메라별 시작/중지 UX, 반복 연결 오류 이벤트의 묶음 정책.
5. 엣지노드·PC 내부 작업의 서비스 인증 및 HTTPS 배포 방식.
6. 실시간 영상 송출 방식, 알림 전달·중복 방지 방식, 파일 정리·보존 기간.

첫 검증은 단일 웹캠에서 로컬 추적 종료 후 새 로컬 기록으로 재등장했을 때 글로벌 ID가 연결되는지 확인한다. 다른 사람이 기존 ID에 잘못 연결되지 않는지도 확인한다. 이는 기본 재식별 흐름 검증이며, 다중 카메라의 시점·조명 차이와 동시 관측 정확도를 검증한 것으로 보고하지 않는다.
